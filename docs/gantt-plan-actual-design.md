# Gantt予定・実績比較 詳細設計（Issue #4）

> 状態: 実装済み。APIモック・.NET全テスト・Chromium表示で検証。実GitLab CE接続は未検証。

## 目的・画面
- GanttはIssue単位、プロジェクトごとに折りたたみ。担当者フィルタ、Issueへのリンク、日・週・月切替を維持。
- 1 Issue行の同じ時間軸に予定バー（上）と実績バー（下）を重ねて比較する。色と凡例、ツールチップで区別する。
- **プロジェクト単位のバー色分けを廃止**し、全プロジェクトで予定=`#7DA9E8`（青）、実績=`#239B77`（緑）に統一する。プロジェクトの識別は見出し・折りたたみ・名称で行う。
- 予定・実績は上下位置と凡例・ツールチップでも区別し、色だけに依存しない。期限超過・工数超過はバーの基本色を変更せず、マーカーや工数表示で強調する。
- 色は共通のCSS変数として定義し、プロジェクトIDや表示順による色生成・色割当ロジックは削除する。
- Issue名の右側に「実績 / 見積もり」の工数列を固定表示し、タイムラインのみ横スクロール。見積もり未設定は「—」とし、実績が見積もりを超過した場合は強調。
- Gantt上部に選択中マイルストーンの開始日・期限を表示。時間軸にマイルストーン期間を背景帯として描画。今日線も表示。

## 予定期間
- 開始: マイルストーンのstart_date（Issue固有の開始日ではないため補完扱い）。
- 終了: Issueのdue_date、なければマイルストーンのdue_date（補完扱い）。
- 開始日・終了日の欠落または開始>終了は予定バーを描画せず、**空文字・空欄**にする。「日程未設定・不正」等の代替文字列は表示しない。
- Issue行と工数表示は維持。予定が空欄でも実績は独立して描画する。

## 実績期間
- 開始: Issueを自動クローズ対象とするMRのうち、最も早いcreated_at。
- 終了: Issueのclosed_at。Openの場合は今日までのバーを「進行中」として描画する（今日を確定した終了日として保存しない）。
- MRが見つからない、または実績開始日を確定できない場合、実績バーは空欄。Closedだがclosed_atが取得できない場合も、終了日を捏造しない。
- 日付はGitLabの日時を明示したタイムゾーンでDateOnlyへ変換。開始>終了の場合は実績バーを描画せず、ログ等で診断可能にする。

## IssueとMRの関連付け
- 運用上の正規ルールはMR説明文の `Closes #123` 等のGitLab自動クローズ連携。
- 候補取得: `GET /projects/:id/issues/:issue_iid/related_merge_requests`。
- 関連の確定: `GET /projects/:id/merge_requests/:merge_request_iid/closes_issues` 等で対象Issueが実際のクローズ対象か検証。候補取得だけでは自動クローズMRと断定しない。
- GitLab CEの稼働バージョンでAPIの存在・応答を実測。API非対応の場合は仕様を勝手に緩めず、代替手段と精度をPRで報告して判断を仰ぐ。
- project_idとissue_iid（必要ならglobal issue id）を組み合わせて照合。複数MRは最も早い作成日。ページング・キャッシュ・レート制限・N+1対策を実装する。

## API・モデル
- Issue取得DTOに `closed_at` を追加。
- Gantt DTOに予定期間・実績期間を別フィールドとして保持し、補完状態、進行中フラグ、ProjectId/Name、IssueUrl、工数秒数を含める。
- 既存APIの破壊的変更を最小化し、フロントで予定・実績の意味を取り違えない命名とする。
- GitLab APIエラー時の扱いは欠落データと区別し、ログにはトークンを出さない。

## 受入テスト
1. 予定・実績が共にあるIssueで上下2本のバーが正しい日付位置に表示される。
2. 予定の片側未設定・逆転はバー領域が完全に空欄、Issueと工数は残る。
3. 予定が無効でも実績が有効なら実績バーが表示される。
4. 複数MRでは最も早い作成日、単なる関連MRは除外。
5. Openは進行中、Closedはclosed_atで終了。MRなしは実績バー空欄。
6. 実績/見積工数、未見積もり、超過強調、マイルストーン帯、日・週・月、折りたたみ、担当者フィルタを検証。
8. 異なるプロジェクトの予定バーはすべて同じ青、実績バーはすべて同じ緑。凡例と上下位置で識別でき、プロジェクト別配色が残っていない。
7. .NET 10のrestore/build/test、CSS Isolationの読み込み、実ブラウザ表示を検証。

## 実装運用
Issue #4 / Draft PRで管理。Codexは実装・テスト後、PRに結果と未検証事項を記載。マージはレビューとユーザー承認後。

## 実装・検証結果
- 予定と実績を独立したnullable日付として返す。予定無効でも実績を描画し、欠落時の代替文字列は表示しない。
- MRはrelated_merge_requestsで列挙し、closes_issuesのproject_id・iid・id一致を検証。ページング、4リクエストの同時実行上限、同一MRの重複取得抑制、選択Issue単位の5分キャッシュを使用。
- 日付はGitLab__TimeZoneId（既定Asia/Tokyo）で変換し、APIのAsOfDateを画面の今日線・進行中表示にも使用。
- API失敗は空データに変換しない。実GitLab CEのバージョン互換性は配備先で要確認。404等が返る場合も関連MRを自動クローズMRとみなす代替処理は行わない。
- 単体テストとChromiumで2段バー、共通配色、工数、空欄、帯・今日線、日週月、折りたたみ・担当者フィルタを確認。実GitLab用テストは認証未設定でスキップ。
